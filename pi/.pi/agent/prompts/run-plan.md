Execute the current plan for: $ARGUMENTS

Load `ops` and `dev`; read `~/.agents/skills/ops/references/plan-memory.md` for selection, format and revisions. This execution workflow also applies when the user directly authorizes execution of an existing plan; the extra approval UI in step 2 is specific to an explicit `/run-plan` invocation. Load `architect` only for a material design question; do not redesign an approved plan merely to execute it.

1. Resolve with `get_current_plan` and read the Markdown contract, Current Step, next authorized task, acceptance, and validation. Before execution, contrast the current plan with relevant later user decisions available in context; if there is a material contradiction, stop and ask for clarification; otherwise continue without additional verification. Apply the shared plan-memory selection/resumption rules; missing, ambiguous, stale-worktree, incomplete, or unresolved plans need an actionable blocker, not a guessed alternative.
2. Explain the scope, purpose, material risks, stop rules, and validation. For `/run-plan`, obtain separate implementation approval through the question tool/UI once; no worker or implementation before confirmation. Cancellation preserves the plan and ends the attempt. For direct execution, respect the user's authorized scope without adding this command-specific gate.
3. After authorization, set `in-progress` and record the current task before work. Follow dependencies and acceptance one bounded slice at a time: each worker stops after its task; the coordinator inspects its diff and verifies acceptance before assigning dependent work. Parallelize only independent slices expressly permitted by the plan, without overlapping writes or checks requiring a stable tree.
4. Assign each worker one bounded task, plan path/task ID and ops' brief; include applicable `dev` criteria in Known under ops' selective skill-handoff rule. The coordinator alone records progress after inspecting the diff for scope and the smallest sufficient change and verifying acceptance with permitted checks. Check off a task only when agreed evidence establishes its outcome, not on child success. If implemented but required verification is missing, keep it unchecked and record implementation, missing evidence and the task-specific blocker. Update Current Step, evidence, checks/results and blockers. Report milestone deltas, not repeated inventories or raw child reports.
5. Workers stop after their assigned task; the coordinator continues through authorized, dependency-ready work after verifying and recording each outcome. A blocked task does not block unrelated work. Milestone reports are progress updates, not completion. Stop when the authorized scope is complete, no remaining authorized work can advance without user intervention, or a safety/approval boundary, material ambiguity, scope conflict or repeated failure without new evidence requires stopping. Authorization for one task does not authorize the rest of the plan or bypass separate approvals. Preserve resumable evidence on partial/blocked/cancelled/timed-out outcomes. On resume, skip only work whose acceptance remains valid; recheck stale evidence.
6. Apply the changelog policy on the final tree. Report the checks that ran (commands/results) and those that did not, the status, unresolved work, and the next action. Full validation uses project-specific commands only on explicit user request; user-confirmed checks are evidence, not agent executions or authorization to rerun them. No commits, remote changes, or automatic plan-reviewer calls.
