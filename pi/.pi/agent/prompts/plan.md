Create a plan for: "$ARGUMENTS"

Use `ops` for the canonical Goal/Known/Evidence/Acceptance/Checks/Stop brief and plan format, and `architect` for design criteria. This is planning only: implementation files are read-only; the session plan may be updated.

Follow this order:

1. Identify the document. Invoking `/plan` explicitly requests persisted planning, so call `create_session_plan` once and use its exact returned path, reusing the active selection. Before delegation, record only the user's brief, decisions, existing changes, evidence, and unresolved questions; do not populate it with your own implementation checklist. Explicit adoption or `newPlan=true` is confirmed by the selection tool's UI. Cancellation leaves the previous selection/documents unchanged and ends the attempt. Selection never authorizes implementation.
2. Prepare directly and cheaply: inspect only the minimum local evidence needed to frame the contract, using `get_current_plan` or `summarize_worktree` where useful. Preparation is not a full architecture investigation and does not pre-solve the design.
3. Delegate the design. `planner` is mandatory inside `/plan`, even for a seemingly simple request; use ordinary workflows outside this command when no persisted plan is wanted. Do not draft a competing plan before or after the child, or bypass it because other workflows allow direct work.
4. Propose `openai-codex/gpt-6.1-sol` profile `low` by default. Use `medium` for material dependencies, competing designs, or unresolved trade-offs; use `high` for substantial architectural uncertainty or high-impact risk where medium is inadequate. Explain the concrete reason, not file count or task length. Present the brief, exact model/thinking, and availability, then invoke `subagent` with agent `planner`, the profile, `profileReason`, and the prepared contract. Pass a reason for low too. The launcher's UI obtains the single approval and may let the user select another available level; do not ask a duplicate question. No UI, an unavailable selection, or cancellation does not authorize a fallback, another role, or direct planning. Report the blocker or `Status: cancelled` and stop.
5. Integrate the returned proposal into the same document. Preserve the planner's checklist and ordering, all material evidence, and unresolved questions; remove only genuine duplication. If the child is partial or blocked, retain that status instead of filling gaps by designing the missing solution yourself.
6. Save the complete plan using the existing ops headings and structure: TL;DR, Goal, Spec / Contract, Current Step, ordered top-level Tn Tasks, risks/stop rules, validation policy, checks, and unresolved items as applicable. State verifiable task outcomes and preserve the agreed objective, constraints, behavior, material decisions/reasons, implemented-versus-verified progress, pending work, blockers and next action. Add exact files, symbols, commands, rationale, dependencies, acceptance or validation details when they prevent ambiguity or are needed to execute and verify; do not enumerate routine reads, commands or edits. Record checks actually run and their results. Scale detail to the continuity needed, without duplicating available inventories or instructions.
7. Read back the entire saved file, using bounded chunks if needed, and verify all material details and referenced task IDs. A truncated preview is insufficient. If saving or verification fails, report blocked; never claim planning is complete.
8. Follow APPEND_SYSTEM's human-facing communication rule. Report complete, partial, or blocked planning separately from implementation. Explain what will change and why, material implications and untouched behavior, and real risks or decisions. Lead with outcomes rather than task IDs or file lists. Put the plan path at the end as a reference, not instead of the explanation. No code implementation or application test-suite success is implied by a saved plan.
